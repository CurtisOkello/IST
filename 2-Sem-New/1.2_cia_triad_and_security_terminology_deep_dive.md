# PART 1: The CIA Triad - Deep Dive

## 1.1 Introduction

The **CIA Triad** is the foundational model for reasoning about information security. It answers one question: *what properties of information must be preserved?* Every security control, every finding in a penetration test report and every SOC alert can be traced to the violation (or protection) of at least one of the three properties.

| Pillar | One-line meaning | Failure state |
|--------|------------------|---------------|
| **Confidentiality** | Only authorized entities can read the information | **Disclosure** |
| **Integrity** | Information is accurate, complete and changed only by authorized entities in authorized ways | **Alteration** |
| **Availability** | Authorized entities can access information and systems when needed | **Destruction / Denial** |

> **Analyst mindset:** When triaging an alert, always ask, "Which pillar is under attack, and has it already been violated?" This determines severity, containment strategy and notification obligations.

### Important Nuances

- The pillars are **independent**: an attacker can violate one without touching the others. Exfiltrating a database breaks confidentiality while leaving integrity and availability intact.
- The pillars are **in tension**: strengthening one often weakens another (see Section 1.8).
- The triad is **context-weighted**. A hospital ICU monitor prioritizes **availability and integrity**; a classified intelligence repository prioritizes **confidentiality**; a financial ledger prioritizes **integrity**.

## 1.2 Confidentiality - Exhaustive Breakdown

### Definition

**Confidentiality** is the property that information is **not made available or disclosed to unauthorized individuals, entities or processes**. It is enforced through a combination of **identity verification, access decisions and cryptographic protection**.

### Sub-properties and Related Concepts

| Concept | Meaning | Technical Example |
|---------|---------|-------------------|
| **Identification** | A claim of identity | Username, certificate subject, API key ID |
| **Authentication (AuthN)** | Proof of the claimed identity | Password + TOTP, FIDO2/WebAuthn key, client certificate |
| **Authorization (AuthZ)** | Determination of permitted actions | RBAC role check, ACL, OAuth 2.0 scopes |
| **Least privilege** | Minimum rights required for the task | Database account with `SELECT` only on one schema |
| **Need-to-know** | Access limited to those with a legitimate purpose | Compartmentalized project folders |
| **Privacy** | Confidentiality applied to personal data | Pseudonymization, consent management |
| **Data classification** | Label that drives handling rules | Public, Internal, Confidential, Restricted |
| **Forward secrecy** | Compromise of long-term keys does not expose past sessions | Ephemeral (EC)DHE key exchange in TLS 1.3 |

### The Three Data States

Confidentiality must be protected in each state, using different mechanisms:

| State | Description | Primary Threats | Primary Controls |
|-------|-------------|-----------------|------------------|
| **At rest** | Stored on disk, database, backup, cloud object store | Stolen drives, misconfigured storage buckets, backup theft, SQL data dumps | Full-disk encryption, **AES-256** (e.g., AES-256-GCM or XTS), transparent database encryption, KMS/HSM key management |
| **In transit** | Moving across a network | Sniffing, **Man-in-the-Middle (MitM)**, ARP spoofing, rogue access points, SSL stripping | **TLS 1.3**, IPsec/WireGuard VPN, SSH, HSTS |
| **In use** | Loaded in memory, being processed | **Credential dumping** from memory, memory scraping malware, cold-boot attacks, side channels | Credential Guard, Protected Process Light (PPL) for LSASS, confidential computing (TEE/enclaves), EDR |

### Cryptographic Detail: AES-256 at Rest

- **AES** (Advanced Encryption Standard) is a **symmetric block cipher** with a 128-bit block size and key sizes of 128, 192 or 256 bits.
- **AES-256** uses a 256-bit key and 14 rounds. Brute force of a 256-bit keyspace is computationally infeasible with any foreseeable classical hardware.
- **Mode of operation matters as much as key size.**
  - **ECB** is insecure: identical plaintext blocks produce identical ciphertext blocks, leaking patterns.
  - **CBC** requires a random IV and offers no authentication (vulnerable to padding-oracle attacks if misused).
  - **GCM** is an **AEAD** mode (Authenticated Encryption with Associated Data). It provides **confidentiality and integrity together**. Reusing a nonce with the same key in GCM is catastrophic.
  - **XTS** is designed for disk/sector encryption.
- **Key management is the real security boundary.** Encryption with a key stored beside the ciphertext provides near-zero protection. Use **envelope encryption** (a data encryption key wrapped by a key-encryption key in a KMS/HSM), rotation and separation of duties.

### Cryptographic Detail: TLS 1.3 in Transit

TLS 1.3 (RFC 8446) improves materially on TLS 1.2:

- **Removes legacy and weak features:** RSA key transport, static Diffie-Hellman, CBC cipher suites, RC4, SHA-1, compression, renegotiation.
- **Mandatory forward secrecy** through ephemeral (EC)DHE key exchange.
- **AEAD-only cipher suites** (e.g., `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`).
- **Faster handshake:** one round trip (1-RTT) for a full handshake; optional **0-RTT** resumption (note: 0-RTT early data is **replayable**, so use only for idempotent requests).
- **Encrypted handshake:** most handshake messages after ServerHello (including certificates) are encrypted, reducing passive metadata exposure.
- **Authentication** of the server (and optionally client) through X.509 certificates validated against a trust chain.

### Access Control Models

| Model | Principle | Typical Use |
|-------|-----------|-------------|
| **DAC** (Discretionary) | Resource owner decides access | Standard file permissions |
| **MAC** (Mandatory) | Central policy and labels decide access | Military, SELinux |
| **RBAC** (Role-Based) | Permissions assigned to roles; users assigned to roles | Enterprise applications, Active Directory groups |
| **ABAC** (Attribute-Based) | Policy evaluates user, resource and environment attributes | Cloud IAM conditions, Zero Trust policy engines |

### Multi-Factor Authentication (MFA)

MFA combines **two or more independent factor categories**: something you **know**, **have** or **are**.

| Method | Phishing-Resistant? | Notes |
|--------|---------------------|-------|
| SMS OTP | No | Vulnerable to SIM-swap and interception |
| TOTP app (RFC 6238) | No | Can be relayed by adversary-in-the-middle phishing kits |
| Push notification | Weak | Vulnerable to **MFA fatigue / push bombing** |
| **FIDO2 / WebAuthn** security key | **Yes** | Cryptographic origin binding defeats credential relay |
| Client certificate / smart card | Yes | Requires PKI operations |

### Confidentiality Attack Detail

- **Credential dumping** (MITRE ATT&CK **T1003**): adversaries with sufficient privilege extract credential material from the **LSASS process memory** (T1003.001), the **SAM database** (T1003.002), **NTDS.dit** on domain controllers (T1003.003) or Linux `/etc/shadow` (T1003.008). Stolen **NTLM hashes** can be reused directly in **Pass-the-Hash** attacks without cracking.
- **Kerberoasting** (T1558.003): any authenticated domain user can request service tickets for accounts with SPNs and crack the encrypted portion **offline**, because it is encrypted with the service account's password-derived key.
- **Man-in-the-Middle** (T1557): **ARP spoofing**, **rogue DHCP**, **LLMNR/NBT-NS poisoning** (T1557.001), evil-twin Wi-Fi, SSL stripping and malicious proxies.
- **NTLM relay**: captured authentication attempts are relayed to another service to gain access without knowing the password.
- **Adversary-in-the-Middle phishing** (reverse-proxy kits): capture **session cookies** after the victim completes MFA, bypassing non-phishing-resistant factors.
- **Data exfiltration** (TA0010): over C2 channels, DNS tunneling, cloud storage APIs and web services.
- **Cloud misconfiguration**: publicly readable object storage, overly permissive IAM, leaked keys in public repositories.
- **Insider threat** and **shoulder surfing**/**physical theft**.

## 1.3 Integrity - Exhaustive Breakdown

### Definition

**Integrity** is the property that information and systems are **accurate, complete and unaltered except by authorized parties through authorized means**. It has two main facets:

- **Data integrity:** content has not been modified, inserted or deleted without authorization.
- **System integrity:** the system performs its intended function without unauthorized manipulation (for example, binaries, configurations and firmware are genuine).

### Sub-properties

| Concept | Meaning | Mechanism |
|---------|---------|-----------|
| **Accuracy and completeness** | Data reflects reality and nothing is missing | Input validation, referential integrity, checksums |
| **Authenticity** | Data genuinely originates from the claimed source | Digital signatures, **HMAC** |
| **Non-repudiation** | A party cannot credibly deny an action | Digital signatures, trusted timestamping, tamper-evident logs |
| **Consistency** | Data is the same across systems and time | ACID transactions, replication integrity |
| **Provenance and chain of custody** | Trusted history of handling | Audit logs, forensic hashing |

### Cryptographic Detail: SHA-256 Hashing

- **SHA-256** is a member of the **SHA-2** family. It maps arbitrary-length input to a fixed **256-bit (32-byte) digest**.
- Required properties of a cryptographic hash:
  - **Preimage resistance:** given a digest, it is infeasible to find any input that produces it.
  - **Second-preimage resistance:** given an input, it is infeasible to find a *different* input with the same digest.
  - **Collision resistance:** it is infeasible to find any two distinct inputs with the same digest.
  - **Avalanche effect:** a one-bit input change flips roughly half of the output bits.
- **MD5 and SHA-1 are broken for collision resistance** and must not be used for integrity assurance where an adversary is involved. They persist in legacy systems and appear in older IoC feeds.
- **Critical distinction:** a plain hash detects *accidental* corruption but provides **no authenticity**. An attacker who can modify the file can also recompute the hash. To defend against malicious tampering, the hash must be **protected**:
  - Using a **keyed hash (HMAC-SHA-256)**, which requires a shared secret, or
  - Using a **digital signature** over the hash, which requires a private key.
- **Do not use fast hashes (SHA-256) for password storage.** Use a slow, salted, memory-hard function such as **Argon2id, scrypt, bcrypt or PBKDF2** so offline cracking is expensive.

**Practical example (hash verification):**

```bash
# Verify a downloaded installer against the publisher's signed checksum
sha256sum installer.tar.gz
# Compare output to the checksum published via a separate, trusted channel
# and verify the signature on the checksum file:
gpg --verify SHA256SUMS.sig SHA256SUMS
```

### File Integrity Monitoring (FIM)

**FIM** establishes a **trusted baseline** (hash, permissions, owner, size, timestamps, ACLs and registry values) of critical files and detects deviations.

| Tool | Approach | Notes |
|------|----------|-------|
| **Wazuh (syscheck)** | Scheduled and **real-time** monitoring of directories and Windows registry keys; compares to a baseline database; supports `who-data` auditing on supported platforms | Open-source XDR/SIEM; alerts flow into the Wazuh rule engine and dashboard |
| **Sysmon** (Sysinternals) | Kernel-level telemetry written to the Windows Event Log | Not a classic baseline FIM, but its events detect integrity-relevant changes (see below) |
| **OSSEC / AIDE / Tripwire** | Hash-database comparison | Classic host-based IDS approach |
| **Auditd (Linux)** | Kernel audit framework watching file paths and syscalls | Often paired with Wazuh |

**Useful Sysmon Event IDs for integrity investigations:**

| Event ID | Meaning | Integrity Use Case |
|----------|---------|--------------------|
| **1** | Process creation (with hashes, parent process, command line) | Detect unexpected binaries and suspicious parent-child chains |
| **3** | Network connection | Identify processes beaconing out |
| **7** | Image/DLL loaded | DLL side-loading detection |
| **11** | File created | New executables in unusual paths |
| **12, 13, 14** | Registry object create/delete, value set, rename | Persistence keys (Run keys), security setting tampering |
| **15** | File stream created | Alternate Data Streams, Mark-of-the-Web removal |
| **23, 26** | File delete (archived / logged) | Evidence destruction, wiper activity |

**Operational best practices for FIM:**

- Monitor **high-value paths**: `/etc`, `/bin`, `/usr/bin`, web roots, Windows `System32`, startup folders, scheduled-task directories and critical registry hives.
- **Tune aggressively** to avoid alert fatigue from legitimate patching and log rotation.
- **Protect the baseline** and forward events **off-host** immediately, because attackers with root can modify local logs and databases.

### Digital Signatures and PKI

A **digital signature** provides **integrity, authenticity and non-repudiation**.

**Signing process:**

1. The sender computes a **hash** of the message (e.g., SHA-256).
2. The sender **encrypts/signs the hash with their private key** (RSA-PSS, ECDSA or **Ed25519**).
3. The receiver recomputes the hash and **verifies the signature using the sender's public key**.
4. If the values match, the content is unaltered **and** was signed by the private-key holder.

**Public Key Infrastructure (PKI)** binds public keys to identities:

| PKI Element | Role |
|-------------|------|
| **Certificate Authority (CA)** | Issues and signs certificates; root CAs are the trust anchors |
| **Intermediate CA** | Issues end-entity certificates; protects the offline root |
| **X.509 certificate** | Contains subject, public key, validity, extensions, issuer signature |
| **Chain of trust** | End-entity, then intermediate, then root, validated by the client |
| **CRL / OCSP** | Revocation mechanisms; OCSP stapling improves performance and privacy |
| **Certificate Transparency (CT)** | Public append-only logs that expose mis-issued certificates |

**Applied examples:** **code signing** (Authenticode, Apple notarization), **software update verification**, **secure boot**, **signed container images**, **DKIM/S/MIME** for email, and **signed firmware**. Supply-chain attacks often succeed by **compromising or abusing signing keys and build pipelines**.

### Other Integrity Controls

- **Input validation and parameterized queries** (prevent injection).
- **Change management** and **peer-reviewed deployment** pipelines.
- **Immutable infrastructure** and **read-only file systems/containers**.
- **Database constraints, transactions (ACID)** and **audit tables**.
- **Write-Once-Read-Many (WORM)** storage and **append-only / hash-chained logs**.
- **Application allow-listing** (WDAC, AppLocker) and **Secure Boot/measured boot (TPM)**.

### Integrity Attack Detail

- **SQL Injection (SQLi)** (T1190 on public-facing apps): unsanitized input is interpreted as SQL. Beyond reading data (confidentiality), attackers use `UPDATE`, `INSERT` and `DELETE` to **alter records**, add privileged accounts or modify prices. **Defense:** parameterized queries/prepared statements, ORM safety, least-privilege DB accounts, WAF as a compensating control.
- **Ransomware encryption** (T1486, *Data Encrypted for Impact*): files are **irreversibly modified** (encrypted) without authorization. This is simultaneously an **integrity violation** (data altered) and an **availability violation** (data unusable). Modern **double and triple extortion** also adds a confidentiality violation through prior exfiltration.
- **Web defacement and content tampering.**
- **Supply-chain compromise:** trojanized updates and poisoned dependencies (e.g., malicious packages on public registries, compromised build servers).
- **Log tampering and indicator removal** (T1070): clearing Windows event logs, modifying timestamps (timestomping, T1070.006).
- **Man-in-the-Middle modification** of unauthenticated traffic.
- **Firmware/bootkit implants** and **registry/config tampering** for persistence.
- **Business Email Compromise (BEC)** altering payment details; **deepfake or forged documents**.
- **Data poisoning** of machine-learning training sets or telemetry.

## 1.4 Availability - Exhaustive Breakdown

### Definition

**Availability** is the property that **systems, services and data are accessible and usable on demand by authorized users**. It is quantified, not merely asserted.

### Key Metrics

| Metric | Definition | Use |
|--------|------------|-----|
| **Uptime %** ("nines") | Proportion of time service is operational | SLA commitments |
| **RTO** (Recovery Time Objective) | Maximum tolerable time to restore service | Drives DR architecture |
| **RPO** (Recovery Point Objective) | Maximum tolerable data loss measured in time | Drives backup/replication frequency |
| **MTBF / MTTR** | Mean time between failures / to repair | Reliability engineering |
| **MTD** (Maximum Tolerable Downtime) | Point beyond which the business is threatened | Business Impact Analysis |

| Availability | Max downtime per year | Max downtime per month (30 days) |
|--------------|----------------------|----------------------------------|
| 99% ("two nines") | ~3.65 days | ~7.2 hours |
| 99.9% ("three nines") | ~8.76 hours | ~43.2 minutes |
| 99.99% ("four nines") | ~52.6 minutes | ~4.3 minutes |
| 99.999% ("five nines") | ~5.26 minutes | ~26 seconds |

### Availability Attack Detail

- **Distributed Denial of Service (DDoS)** (T1498 Network DoS, T1499 Endpoint DoS): volumetric, protocol and application-layer categories.

| DDoS Category | OSI Layer | Mechanism | Examples |
|---------------|-----------|-----------|----------|
| **Volumetric** | L3/L4 | Saturate bandwidth | **Reflection/amplification** using spoofed source IPs against open DNS, NTP, memcached, CLDAP; UDP floods |
| **Protocol** | L3/L4 | Exhaust state tables of servers, firewalls and load balancers | **SYN flood**, ACK floods, fragmentation attacks |
| **Application-layer** | L7 | Exhaust application resources with seemingly legitimate requests | HTTP GET/POST floods, **Slowloris** (holding connections open), **HTTP/2 Rapid Reset** (CVE-2023-44487), expensive search or login endpoint abuse |

- **Botnets:** networks of compromised hosts (often IoT devices and routers) under C2 control. The **Mirai** family demonstrated mass compromise of devices with default credentials.
- **Resource exhaustion:** CPU, memory, disk, file descriptors, database connection pools, **algorithmic complexity attacks** (e.g., ReDoS regular expression denial of service), fork bombs and log-volume filling.
- **Ransomware:** data and systems rendered unusable until recovery.
- **Destructive wipers** (T1485, T1561): intentionally destroy data and disk structures.
- **DNS and BGP attacks:** DNS hijacking, authoritative server flooding, **BGP route hijacking/leaks** diverting or black-holing traffic.
- **Non-malicious causes:** hardware failure, misconfiguration, failed changes, expired certificates, power loss, natural disaster and cloud provider outages.

### Availability Controls in Depth

#### High Availability (HA) Clusters

| Pattern | Description | Trade-offs |
|---------|-------------|------------|
| **Active-Passive (failover)** | Standby node takes over on failure | Simpler; unused capacity; failover delay |
| **Active-Active** | All nodes serve traffic simultaneously | Better utilization; requires session/state handling |
| **N+1 / N+M redundancy** | Spare capacity for failures | Cost vs resilience |

- Key mechanisms: **heartbeat/health checks**, **quorum** (to avoid split-brain), **floating/virtual IPs (VRRP, keepalived)**, **shared or replicated storage**, automated failover (e.g., Pacemaker/Corosync, database replication with automatic promotion, Kubernetes ReplicaSets).
- Eliminate **single points of failure (SPOF)** at every layer: power (dual PSU, UPS, generator), network (redundant links and switches, multi-homing), compute, storage (RAID, replication), DNS, and geography (multi-AZ, multi-region).

#### Load Balancing

- **L4 load balancers** distribute TCP/UDP flows; **L7 load balancers** route on HTTP attributes and can terminate TLS, enforce rate limits and integrate WAF.
- Algorithms: round robin, least connections, weighted, IP hash, and latency-based.
- **Health checks** remove failed backends automatically; **connection draining** supports graceful maintenance.
- Security role: absorb and distribute surges, hide origin infrastructure, and apply **rate limiting**, **connection limits** and **SYN cookies**.

#### BGP Anycast for DDoS Mitigation

- In **Anycast**, the **same IP prefix is announced via BGP from multiple geographically distributed locations**. Internet routing delivers each packet to the **topologically nearest** announcing site.
- **DDoS benefit:** attack traffic is **dispersed across many points of presence** (each botnet source is naturally routed to its nearest site), so no single location receives the full volume. Capacity is aggregated across the whole network.
- **Scrubbing centers:** suspicious traffic is diverted (via BGP announcement or DNS) to facilities that filter malicious packets and forward clean traffic (often via **GRE tunnels** or direct interconnect).
- Related techniques: **RTBH** (Remotely Triggered Black Hole) to drop traffic to a victim IP (sacrificing that IP to protect the network), **BGP Flowspec** for granular filtering, **ingress filtering/BCP38** to limit spoofing, **upstream ISP coordination**, CDN and cloud DDoS protection, and **always-on vs on-demand** protection models.
- Layer-7 defenses complement this: **WAF**, **bot management**, **challenge pages**, **rate limiting**, caching and **autoscaling with cost guards**.

#### The 3-2-1 Backup Strategy

| Element | Meaning |
|---------|---------|
| **3** copies of data | Production plus two backups |
| **2** different media/storage types | E.g., disk plus tape, or disk plus cloud object storage |
| **1** copy offsite | Protects against site-level disaster |

- **Modern extension: 3-2-1-1-0** adds **1 offline/air-gapped/immutable copy** (object lock, WORM, tape) and **0 errors** confirmed by regular **restore testing**.
- **Ransomware-resilient backups:** separate credentials and administrative domain for backup systems, **immutability**, MFA on backup consoles, network segmentation and monitoring for mass-deletion of snapshots or shadow copies (T1490, *Inhibit System Recovery*).
- **An untested backup is a hope, not a control.** Validate restores against defined **RTO/RPO**.

#### Disaster Recovery Site Types

| Site | Description | RTO | Cost |
|------|-------------|-----|------|
| **Hot** | Fully mirrored, live | Minutes | Highest |
| **Warm** | Equipment ready, data partly current | Hours | Medium |
| **Cold** | Space and power only | Days-weeks | Lowest |

## 1.5 The DAD Triad - The Attacker's Inverse Model

### Definition

The **DAD Triad** is the **adversarial mirror** of the CIA Triad. Where defenders aim to *preserve* a property, attackers aim to *violate* it.

| Defender Goal (CIA) | Attacker Objective (DAD) | Meaning |
|---------------------|--------------------------|---------|
| **Confidentiality** | **Disclosure** | Unauthorized exposure of information |
| **Integrity** | **Alteration** | Unauthorized modification of information or systems |
| **Availability** | **Destruction** (or **Denial**) | Unauthorized removal or disruption of access to information or services |

### Using DAD for Attack Modeling

Threat actors (and red teams) begin with an **objective**, then work backward to a technique. Defenders use the same logic during **threat modeling** (e.g., **STRIDE** maps well onto CIA/DAD).

| STRIDE Category | Violated Property | DAD Objective |
|-----------------|-------------------|---------------|
| **S**poofing | Authentication (supports C and I) | Enables disclosure/alteration |
| **T**ampering | Integrity | **Alteration** |
| **R**epudiation | Non-repudiation (integrity of accountability) | Alteration of evidence |
| **I**nformation disclosure | Confidentiality | **Disclosure** |
| **D**enial of service | Availability | **Destruction/Denial** |
| **E**levation of privilege | Authorization (supports all three) | Enables all objectives |

### Attacker Objective Examples

- **Espionage APT:** primary objective **Disclosure**, with long dwell time and minimal noise.
- **Ransomware affiliate:** objectives of **Disclosure** (for extortion), **Alteration/Destruction** (encryption), and **Denial** of recovery.
- **Hacktivist:** objectives of **Disclosure** (leaks), **Alteration** (defacement) and **Denial** (DDoS) for visibility.
- **Fraudster:** objective **Alteration** (changing payment details, balances).
- **Destructive nation-state operator:** objective **Destruction** (wipers) to cripple infrastructure.

### Chaining Objectives

Real intrusions often **sequence** DAD objectives. A typical ransomware campaign:

1. **Disclosure first:** credentials dumped, network mapped, data exfiltrated.
2. **Alteration:** backups tampered with, security tools disabled, logs cleared.
3. **Destruction/Denial last:** encryption detonation across the estate.

> **SOC implication:** detecting the early **Disclosure** stage (credential access, discovery, exfiltration staging) provides the window to stop the **Destruction** stage.

| **Availability** | **Botnet C2-driven attacks** | Coordinated compromised hosts | T1498, T1584.005 | Beaconing patterns, known botnet IPs |
| **Availability** | **Resource exhaustion / ReDoS** | CPU/memory/connection starvation | T1499 | CPU saturation, connection-pool exhaustion |
| **Availability** | **Destructive wiper** | Overwrite disk, MBR, files | T1485, T1561 | Mass deletion events, raw-disk writes, boot failures |
| **Availability** | **Backup destruction** | Delete snapshots, shadow copies | T1490 | `vssadmin delete shadows`, backup-console deletions |

> **Note:** Many attacks cross pillars. Ransomware, for example, is classically **Integrity + Availability**, plus **Confidentiality** when exfiltration precedes encryption. Always classify by *all* pillars affected.

## 1.7 Defensive Controls Mapped to Each Pillar

| Pillar | Control | Technical Specification | What It Mitigates |
|--------|---------|--------------------------|-------------------|
| **Confidentiality** | **Encryption at rest** | **AES-256-GCM/XTS**, TDE, KMS/HSM key custody, envelope encryption, key rotation | Disk/backup theft, storage exposure |
| **Confidentiality** | **Encryption in transit** | **TLS 1.3** (disable TLS 1.0/1.1; prefer 1.3), HSTS, certificate pinning where appropriate, IPsec/WireGuard | Eavesdropping, MitM, SSL stripping |
| **Confidentiality** | **RBAC / ABAC / least privilege** | Role design, privileged access management (PAM), just-in-time access, periodic access reviews | Privilege abuse, lateral movement, insider threat |
| **Confidentiality** | **MFA** | **FIDO2/WebAuthn** preferred; conditional access policies | Credential theft, password spraying, stuffing |
| **Confidentiality** | **Endpoint credential protection** | Windows Credential Guard, LSA protection (PPL), LAPS, tiered admin model, disabling LLMNR/NBT-NS and SMB signing enforcement | Credential dumping, relay attacks |
| **Confidentiality** | **DLP and egress control** | Content inspection, CASB, egress filtering, DNS monitoring | Exfiltration |
| **Integrity** | **Hashing** | **SHA-256/SHA-3**, HMAC-SHA-256, Argon2id for passwords | Undetected modification, weak credential storage |
| **Integrity** | **FIM** | **Wazuh syscheck** (real-time + who-data), AIDE, auditd; Sysmon Event IDs 1, 11, 13, 23 feeding the SIEM | Tampering, web shells, persistence, log manipulation |
| **Integrity** | **Digital signatures and PKI** | RSA-PSS/ECDSA/Ed25519, code signing, signed updates, secure boot, DKIM/S/MIME, CT monitoring | Supply-chain tampering, forged software/email |
| **Integrity** | **Secure development** | Parameterized queries, input validation, SAST/DAST, dependency scanning, SBOM | SQLi, injection flaws, vulnerable libraries |
| **Integrity** | **Change control and immutability** | Peer review, CI/CD gating, immutable images, WORM logs, hash-chained audit trails | Unauthorized or silent change |
| **Availability** | **HA clusters** | Active-active/passive, quorum, VRRP/keepalived, multi-AZ/region | Hardware/software failure, localized outage |
| **Availability** | **Load balancing** | L4/L7, health checks, rate limiting, SYN cookies, autoscaling | Traffic spikes, partial DDoS, backend failure |
| **Availability** | **BGP Anycast + scrubbing** | Multi-PoP Anycast announcements, scrubbing centers, RTBH, Flowspec, BCP38 | Volumetric and protocol DDoS |
| **Availability** | **3-2-1(-1-0) backups** | Immutable/offline copies, separate credentials, tested restores to RTO/RPO | Ransomware, wipers, accidental deletion |
| **Availability** | **Capacity and patch management** | Monitoring, baselining, patch SLAs, configuration management | Resource exhaustion, exploit-driven crashes |
| **Availability** | **BCP/DR planning** | Business impact analysis, tested DR runbooks, tabletop exercises | Major incidents and disasters |

### Defense in Depth

No single control is sufficient. Layer **preventive** (stop), **detective** (see), **corrective** (recover), **deterrent** and **compensating** controls across **physical, network, host, application, data and identity** layers, assuming each layer **will eventually fail**.

## 1.8 The Security vs Usability Trade-off

### Core Tension

Security controls impose **friction**: time, cost, complexity and cognitive load. Business value depends on **speed, convenience and flexibility**. Excessive friction drives **workarounds**, which create **shadow IT** and **new vulnerabilities**.

> **Principle:** The most secure system is often unusable, and unusable systems get bypassed. Security that people avoid is not security.

### Trade-offs Within and Across the Triad

| Tension | Description | Example |
|---------|-------------|---------|
| **Confidentiality vs Availability** | Stronger access restrictions can block legitimate users or emergency access | Overly strict controls in healthcare may delay emergency access to patient records; "break-glass" procedures resolve this with auditing |
| **Confidentiality vs Usability** | Strong authentication adds friction | Frequent forced MFA and complex passwords lead to password reuse and sticky-note passwords |
| **Integrity vs Availability/Speed** | Verification and approval steps slow delivery | Mandatory code signing and review slow release cycles; mitigated through **automated CI/CD gates** |
| **Availability vs Confidentiality** | Replication, caching and CDNs multiply copies of data | More copies and more locations enlarge the attack surface |
| **Encryption vs Visibility** | Pervasive TLS 1.3 prevents passive inspection | SOC loses network visibility; requires TLS inspection, endpoint telemetry or proxy architecture (with its own privacy and risk implications) |
| **Security vs Performance/Cost** | Encryption and inspection add latency and cost | Hardware acceleration (AES-NI) and efficient design reduce overhead |

### Managing the Trade-off Rationally

1. **Risk-based approach:** apply controls proportional to **asset value and threat level**, not uniformly.
2. **Classification-driven security:** tighter controls for Restricted data; lighter for Public.
3. **Adaptive/conditional access:** step-up authentication only for **risky** contexts (new device, unusual location, sensitive action).
4. **Passwordless and SSO** to *reduce* friction while *increasing* security.
5. **Automation:** automated patching, secrets rotation and policy enforcement remove human burden.
6. **Break-glass procedures** with strict logging for emergencies.
7. **Measure friction** (help-desk tickets, MFA failures, exception requests) alongside security metrics.
8. **Engage stakeholders:** define acceptable risk with business owners; document **risk acceptance** formally.

# PART 2: Essential Terminology in Information Security

## 2.1 The Risk Equation: Asset, Vulnerability, Threat, Risk

### Definitions

| Term | Definition | Examples |
|------|------------|----------|
| **Asset** | Anything of **value** to the organization that requires protection: information, systems, people, processes, reputation, reputation and physical infrastructure | Customer database, domain controller, source code repository, payment API, employee credentials |
| **Vulnerability** | A **weakness** in an asset, control, design, process or person that could be exploited | Unpatched software (e.g., a CVE), default credentials, missing input validation, open S3 bucket, untrained staff |
| **Threat** | Any **circumstance or actor with the potential to cause harm** by exploiting a vulnerability | Ransomware operator, insider, malware family, natural disaster, power failure |
| **Threat actor / agent** | The entity that *carries out* the threat | Cybercriminal group, nation-state |
| **Risk** | The **potential for loss or harm** when a threat exploits a vulnerability in an asset; a function of **likelihood** and **impact** | "Probability that an external attacker exploits an unpatched VPN gateway and exfiltrates customer data, causing a regulatory fine and reputational damage" |
| **Impact** | Magnitude of harm if the risk materializes | Financial loss, downtime, legal penalties, safety harm |
| **Likelihood** | Probability that the event occurs | Based on threat capability, vulnerability exposure and existing controls |
| **Control (countermeasure)** | A safeguard that reduces risk | Patch, WAF, MFA, backup |
| **Residual risk** | Risk remaining after controls | Risk after patching but with exposure to zero-days |
| **Inherent risk** | Risk before any controls | Raw exposure |

### The Conceptual Relationship

```
        exploits                targets
THREAT ----------> VULNERABILITY -------> ASSET
   \                                        /
    \------------- produces ---------------/
                       |
                       v
                     RISK  (likelihood x impact)
                       |
                       v
         treated by CONTROLS  -> RESIDUAL RISK
```

- **A threat without a vulnerability poses no risk** to that asset. (A ransomware strain that targets only Windows presents no risk to an isolated Linux appliance.)
- **A vulnerability without a threat** may present low risk (e.g., a flaw on a fully air-gapped, unreachable system), though threats can change.
- **An asset of no value** yields no meaningful risk, regardless of threats and vulnerabilities.

### Mathematical Representations

**Conceptual formulas:**

```
Risk = Threat x Vulnerability x Asset Value
Risk = Likelihood x Impact
Risk = (Threat x Vulnerability) / Countermeasures      (conceptual, illustrative)
```

**Quantitative Risk Analysis (QRA):**

| Term | Formula | Meaning |
|------|---------|---------|
| **AV** | Asset Value | Monetary value of the asset |
| **EF** | Exposure Factor (0-1) | Fraction of asset value lost in one event |
| **SLE** | `SLE = AV x EF` | **Single Loss Expectancy**: cost of one incident |
| **ARO** | Annualized Rate of Occurrence | Expected incidents per year |
| **ALE** | `ALE = SLE x ARO` | **Annualized Loss Expectancy** |
| **Control justification** | `ALE(before) - ALE(after) - annual control cost > 0` | A control is worthwhile if the risk reduction exceeds its cost |

**Worked example:**

- Asset: customer database valued at **$2,000,000** (AV).
- A breach would expose roughly **40%** of its value (EF = 0.40).
- `SLE = 2,000,000 x 0.40 = $800,000`
- Threat intelligence and history suggest **1 successful breach every 4 years** (ARO = 0.25).
- `ALE = 800,000 x 0.25 = $200,000 / year`
- A proposed control (DLP + MFA + hardening) costs **$60,000/year** and reduces ARO to **0.05**.
- `New ALE = 800,000 x 0.05 = $40,000`
- **Risk reduction** = `200,000 - 40,000 = $160,000`; **net benefit** = `160,000 - 60,000 = $100,000/year`. **The control is justified.**

**Qualitative approach:** a **risk matrix** (e.g., 5x5) scores likelihood and impact (Low-Critical) to prioritize work when monetary data is unavailable.

### Risk Treatment Options

| Strategy | Description | Example |
|----------|-------------|---------|
| **Mitigate (reduce)** | Apply controls | Patch, segment network, deploy MFA |
| **Transfer (share)** | Shift financial burden | Cyber insurance, outsourcing to a managed provider (accountability remains) |
| **Avoid** | Stop the risky activity | Decommission a legacy system |
| **Accept (retain)** | Knowingly tolerate within appetite | Document and approve residual risk |

### Vulnerability Scoring Tools

- **CVE** (Common Vulnerabilities and Exposures): unique identifier (e.g., `CVE-2021-44228`).
- **CVSS** (Common Vulnerability Scoring System): severity score 0.0-10.0 (Base, Temporal, Environmental metrics). **Severity is not risk**: context matters.
- **EPSS** (Exploit Prediction Scoring System): probability that a CVE will be exploited in the wild.
- **CISA KEV** (Known Exploited Vulnerabilities) catalog: vulnerabilities confirmed as actively exploited; should be prioritized.
- **CWE** (Common Weakness Enumeration): classification of underlying weakness types (e.g., CWE-89 SQL injection).

> **VAPT insight:** A **Vulnerability Assessment** *identifies and enumerates* vulnerabilities (breadth). A **Penetration Test** *attempts to exploit* them to demonstrate **real, contextual risk and impact** (depth). The deliverable of a good pentest is not a list of CVEs but **evidence-based risk**.

## 2.2 The Attack Chain: Exploit, Payload, Zero-Day

### Definitions

| Term | Definition | Analogy |
|------|------------|---------|
| **Vulnerability** | The **weakness** itself | An unlocked, flawed window latch |
| **Exploit** | **Code, technique or sequence of actions that takes advantage of a vulnerability** to cause unintended behavior (e.g., code execution, privilege escalation, auth bypass) | The method of opening the latch and getting inside |
| **Payload** | The **action performed after successful exploitation**: the code or commands delivered to achieve the attacker's goal | What the intruder does once inside (steals, plants, destroys) |
| **Zero-day (0-day)** | A vulnerability **unknown to the vendor/defenders** (no patch exists); a **zero-day exploit** leverages it. Defenders have had "zero days" to fix it | A flaw nobody inside the building knows about |
| **N-day** | A vulnerability that is **publicly known and usually patched**, yet remains exploitable on unpatched systems | A known broken latch that the owner has not fixed |
| **Proof of Concept (PoC)** | Demonstration that a vulnerability is exploitable; may be non-weaponized | Showing the latch can be forced |
| **Weaponization** | Making an exploit reliable, portable, stealthy and integrated with delivery and payloads | Turning a lab trick into a dependable burglary kit |

### Vulnerability Existing vs Exploit Being Weaponized

This distinction is central to accurate risk assessment:

| Stage | State | Risk Implication |
|-------|-------|------------------|
| **1. Vulnerability exists** | A flaw is present in code/config, possibly undiscovered | Latent risk; exploitation not yet possible by outsiders |
| **2. Vulnerability discovered** | Researcher or attacker identifies it | Risk rises; knowledge asymmetry matters |
| **3. Disclosure / CVE assigned** | Coordinated or public disclosure; patch may be released | Defenders can act; attackers also study the patch ("patch diffing") |
| **4. PoC published** | Demonstration of exploitability | Skilled actors can adapt quickly |
| **5. Weaponized exploit** | Reliable exploit packaged in toolkits, frameworks or malware | **Mass exploitation becomes practical** |
| **6. Exploited in the wild** | Observed in real attacks (CISA KEV, vendor advisories) | **Highest priority**; assume compromise is possible |

> A vulnerability becomes dangerous at scale not when it **exists**, but when a **reliable, accessible exploit** and a **reachable target** coincide. Prioritize remediation using **exploitability evidence (EPSS, KEV)** and **asset exposure**, not CVSS alone.

### Exploit Classification

- **Remote vs local:** remote exploits work over a network; local exploits need prior access (often privilege escalation).
- **Client-side vs server-side.**
- **Memory-corruption** (buffer overflow, use-after-free), **logic flaws** (auth bypass, IDOR), **injection** (SQLi, command injection), **deserialization**, and **misconfiguration abuse**.
- **Zero-click vs user-interaction-required.**

### Payload Concepts (Defender-Level Overview)

- **Staged payloads:** a small initial component retrieves a larger second stage, reducing initial footprint and enabling flexible follow-on actions.
- **Stageless payloads:** the full capability is delivered in one component.
- Common payload objectives: **remote access (C2 beacon), credential theft, persistence, lateral movement tooling, data theft, ransomware encryption, wiper behavior or cryptomining.**
- **Delivery mechanism** (phishing attachment, drive-by download, exploit kit, supply chain) is distinct from both the **exploit** and the **payload**.

### How the Terms Interact: A Single Incident

**Scenario:** A public-facing web application has an unpatched deserialization flaw.

| Term | In this scenario |
|------|------------------|
| **Asset** | The web server and the customer database it connects to |
| **Vulnerability** | Insecure deserialization flaw (CVE) in an application framework |
| **Threat / Threat actor** | An initial access broker or ransomware affiliate scanning the Internet |
| **Exploit** | A crafted request that triggers the flaw, resulting in remote code execution |
| **Payload** | A web shell and C2 beacon that is then used to pull additional tooling |
| **Zero-day or N-day?** | If a patch existed for months, it is an **N-day**. If used before any patch, it is a **zero-day** |
| **Risk** | High: Internet-exposed, exploit public, sensitive data reachable |

### Kill Chain Frameworks

| Framework | Phases (summary) |
|-----------|------------------|
| **Lockheed Martin Cyber Kill Chain** | Reconnaissance, Weaponization, Delivery, Exploitation, Installation, Command & Control, Actions on Objectives |
| **MITRE ATT&CK (Enterprise)** | Reconnaissance, Resource Development, Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command and Control, Exfiltration, Impact |
| **Unified Kill Chain** | Combines in-network, out-of-network and objectives phases |

## 2.3 The Adversary: Threat Actors

### Definition

A **Threat Actor** (threat agent) is an **individual, group or organization that conducts or intends to conduct malicious activity** against an asset. Understanding actors drives **threat modeling, detection engineering and prioritization**, because **capability, motivation, resources and persistence** dictate what controls are needed.

### Threat Actor Comparison

| Attribute | **Script Kiddie** | **Cybercriminal** | **Hacktivist** | **APT (Advanced Persistent Threat)** |
|-----------|-------------------|-------------------|----------------|----------------------------------------|
| **Skill level** | Low; uses prebuilt tools | Moderate to high; often specialized roles | Low to moderate; varies | Very high; custom tooling and tradecraft |
| **Primary motivation** | Curiosity, notoriety, "fun" | **Financial gain** | **Ideology, politics, social cause** | **Strategic: espionage, geopolitical advantage, sabotage, sometimes financial** |
| **Resources** | Minimal | Significant (illicit economy, RaaS, brokers) | Limited; relies on crowds and tools | **Substantial, often state-backed** |
| **Targeting** | Opportunistic, mass scanning | Opportunistic and increasingly targeted ("big game hunting") | Targets symbolizing opposition | **Highly targeted, mission-driven** |
| **Persistence** | Low; gives up quickly | Moderate; campaign-based | Short bursts tied to events | **Long dwell time (months-years)**, stealthy |
| **Typical techniques** | Public exploit tools, default-credential abuse, simple DoS tools | Phishing, ransomware, banking trojans, BEC, infostealers, initial access brokers, exploit of known vulnerabilities | DDoS, defacement, doxxing, data leaks | Zero-days, supply-chain compromise, living-off-the-land, custom implants, advanced evasion |
| **Detection challenge** | Easy; noisy and signature-based | Moderate; many IoCs, fast-moving | Moderate; often visible and public | **Hard; requires behavioral and TTP-based detection, threat hunting** |
| **Example impact** | Defaced small site, minor disruption | Enterprise-wide ransomware, fraud | Service outages, reputational harm | Long-term theft of IP or classified data, critical infrastructure access |

### Additional Actor Types

- **Insider threat:** malicious, negligent or compromised insider with legitimate access.
- **Nation-state actors:** the category that includes most APTs; state-sponsored or state-aligned.
- **Initial Access Brokers (IABs):** sell footholds to other criminals.
- **Ransomware-as-a-Service (RaaS) ecosystems:** developers, affiliates and negotiators operating as a business.
- **Competitors and corporate espionage actors.**
- **Terrorist groups, and "grey-hat" researchers** operating outside authorization.

### APT Characteristics ("Advanced, Persistent, Threat")

- **Advanced:** sophisticated tools, zero-days, custom malware and strong operational security.
- **Persistent:** maintains long-term access, re-entering if evicted, adapting to defenses.
- **Threat:** a **coordinated and resourced** adversary with specific objectives.
- Tracked by vendors and agencies under names such as **APT28, APT29, Lazarus Group, Sandworm** (naming varies across vendors; use MITRE ATT&CK Groups for cross-referencing).

### Why This Matters for the SOC

- **Prioritize detections** by who is likely to target your sector (finance: cybercriminals and state-aligned groups; defense: APTs; media/government: hacktivists).
- **Adjust response:** an opportunistic script kiddie is contained and closed; an **APT presence requires full scoping, eviction planning and assumption that other footholds exist**.

## 2.4 Threat Intelligence: IoCs vs TTPs

### Definitions

- **Indicator of Compromise (IoC):** an **observable artifact** indicating that a system **has been or is being compromised**. IoCs are **atomic, specific and typically machine-matchable**.
- **Tactics, Techniques and Procedures (TTPs):** the **behavioral patterns of an adversary**.
  - **Tactic:** the adversary's *goal* at a stage (the "why"), e.g., **Credential Access**.
  - **Technique:** *how* the goal is achieved (the "how"), e.g., **OS Credential Dumping (T1003)**.
  - **Sub-technique:** a more specific variant, e.g., **LSASS Memory (T1003.001)**.
  - **Procedure:** the **specific implementation** by a given actor or tool, e.g., a particular group using a particular tool and command pattern to dump LSASS.

### Detailed Comparison

| Dimension | **Indicators of Compromise (IoCs)** | **Tactics, Techniques and Procedures (TTPs)** |
|-----------|--------------------------------------|-----------------------------------------------|
| **Nature** | **Static artifacts / evidence** | **Dynamic behaviors / methodology** |
| **Examples** | Malicious **IP addresses**, **domains/URLs**, **file hashes (MD5, SHA-256)**, email sender addresses, **registry keys**, mutex names, filenames, TLS certificate fingerprints (JA3/JA3S) | **T1059.001 PowerShell** execution with encoded commands; **T1053.005 Scheduled Task** persistence; **T1003.001 LSASS** dumping; **T1021.001 RDP** lateral movement; **T1070 log clearing** |
| **Question answered** | "**What** did we observe?" / "Is this artifact known-bad?" | "**How** does the adversary operate?" / "**What would they do next?**" |
| **Ease for attacker to change** | **Trivial**: new IP, recompile for new hash, register new domain (minutes) | **Difficult and costly**: retraining, retooling and changing habits (weeks to months) |
| **Lifespan** | **Short** (hours to weeks); high decay rate | **Long**; behaviors persist across campaigns |
| **Detection method** | Exact-match blocklists, SIEM/IDS signatures, hash lookups, YARA (file-based) | **Behavioral analytics**, correlation rules, **Sigma** rules, EDR behavior detections, threat hunting, ATT&CK-mapped analytics |
| **False positives** | Low per match (exact), but can be stale (reassigned IPs, shared hosting) | Higher; requires **tuning and context** |
| **Coverage** | Catches **known** artifacts only | Can detect **new tools/variants** that use known behaviors |
| **Strengths** | Fast to deploy, automatable, cheap, good for rapid containment | Resilient, strategic, reveals adversary intent and attribution patterns |
| **Weaknesses** | Easily evaded, reactive, perishable | Resource-intensive; needs skilled analysts and good telemetry |
| **Intel level** | **Tactical/operational (technical)** | **Operational/strategic** |
| **Sharing standards** | STIX/TAXII, MISP, OpenIOC | MITRE ATT&CK, Sigma, ATT&CK Navigator layers |

### The Pyramid of Pain (David J. Bianco)

Ranks indicator types by how much **pain** denying them causes the adversary:

| Level (bottom to top) | Indicator Type | Pain to Adversary |
|-----------------------|----------------|-------------------|
| 1 | **Hash values** | Trivial: change one byte |
| 2 | **IP addresses** | Easy |
| 3 | **Domain names** | Simple |
| 4 | **Network/host artifacts** (user-agent strings, registry keys, URI patterns) | Annoying |
| 5 | **Tools** | Challenging: must find or build replacements |
| 6 | **TTPs** | **Tough**: must change fundamental behavior |

> **Strategic takeaway:** Mature SOCs use IoCs for **fast, automated blocking** but invest detection engineering effort in **TTP-based behavioral detections**, climbing the pyramid.

### IoC and TTP Interaction in an Incident

1. **Initial alert (IoC-driven):** the SIEM matches outbound traffic to **IP `203.0.113.50`** listed in a threat-intel feed.
2. **Pivot:** the analyst finds the host and a process whose **SHA-256 hash** matches a known malware sample.
3. **Behavior analysis (TTP):** the EDR timeline shows `winword.exe` spawning `powershell.exe -enc ...` (**T1059.001**), a new Run key (**T1547.001**), then LSASS access (**T1003.001**).
4. **Hunt (TTP-based):** the team searches enterprise-wide for the **same behavior chain**, finding two additional hosts where the **IP and hash differ** (the attacker rotated infrastructure) but the **behaviors are identical**. An IoC-only approach would have missed them.
5. **Output:** new IoCs are added to blocklists *and* new **Sigma/EDR rules** encode the TTPs.

### Intelligence Types

| Type | Audience | Content |
|------|----------|---------|
| **Strategic** | Executives | Trends, actor motivations, risk to the business |
| **Operational** | SOC leads, IR | Campaign details, actor TTPs, timelines |
| **Tactical** | Analysts, engineers | TTPs, detection logic |
| **Technical** | Automated systems | IoCs: IPs, hashes, domains |

## 2.5 Scope: Attack Surface vs Attack Vector

### Definitions

- **Attack Surface:** the **sum of all points (exposures) where an unauthorized user could attempt to enter, interact with, extract data from or disrupt a system or organization**. It describes **what is exposed**: a **static, measurable property of the environment**.
- **Attack Vector:** the **specific path or method an attacker uses to exploit an exposure** and reach the target. It describes **how the attacker gets in**: a **dynamic route of an attack**.

> **Memory aid:** The **attack surface** is the *collection of doors and windows* on the building. The **attack vector** is the *particular door the burglar chooses and how they get through it*.

### Attack Surface Categories

| Category | Examples |
|----------|----------|
| **Digital / network** | Internet-facing hosts and open ports, VPN gateways, APIs, web applications, cloud services, DNS records, exposed management interfaces (RDP, SSH, admin panels), shadow IT, third-party integrations, SaaS tenants |
| **Software** | Libraries and dependencies, outdated components, unvalidated input points, misconfigured services |
| **Human / social engineering** | Employees susceptible to phishing, vishing, smishing; publicly available OSINT on staff; weak security culture |
| **Physical** | Unsecured offices, USB ports, unattended devices, badge cloning, server rooms |
| **Supply chain** | Vendors, managed service providers, open-source packages, firmware and hardware provenance |
| **Identity** | Accounts, service accounts, API keys, tokens, over-privileged roles, leaked credentials |

### Attack Surface Management (ASM)

- **Reduce:** disable unused services, close ports, remove stale DNS records and accounts, decommission legacy systems, apply least privilege, segment networks.
- **Discover:** **external attack surface management** and asset discovery to find unknown/forgotten assets (an unknown asset cannot be defended).
- **Monitor:** continuous scanning, certificate and DNS monitoring, cloud posture management (CSPM).
- **Measure:** number of exposed services, unpatched Internet-facing assets, privileged accounts, and third-party connections.

### Attack Vector Examples

| Vector | Description | Surface it Traverses |
|--------|-------------|----------------------|
| **Phishing email with malicious link/attachment** | Social engineering delivering credential theft or malware | Human, email gateway |
| **Exploitation of public-facing application** (T1190) | Remote exploit against an Internet-exposed web app or VPN | Digital/network, software |
| **Valid accounts / stolen credentials** (T1078) | Logging in with leaked or sprayed credentials | Identity |
| **Brute force / password spraying** (T1110) | Guessing passwords against exposed login portals | Identity, network |
| **Supply-chain compromise** (T1195) | Malicious update or dependency | Supply chain |
| **Removable media** (T1091) | Infected USB drive | Physical |
| **Drive-by compromise** (T1189) | Compromised website exploits browser | Human, software |
| **Misconfigured cloud storage** | Direct access to exposed data | Cloud/digital |
| **Insider** | Abuse of legitimate access | Identity, human |

### Attack Surface vs Attack Vector: Contrast Table

| Aspect | **Attack Surface** | **Attack Vector** |
|--------|-------------------|-------------------|
| **Definition** | Total set of exposed entry points and weaknesses | Specific route or method used to compromise |
| **Perspective** | **Defender's inventory** of exposure | **Attacker's chosen path** |
| **Nature** | Broad, structural, continuous | Specific, situational, per-attack |
| **Unit** | Collection (many points) | Individual path (one chain) |
| **Question answered** | "**Where** are we exposed?" | "**How** did they get in?" |
| **Control strategy** | **Minimize and monitor** (reduce exposure) | **Block, detect and break** (interrupt the path) |
| **VAPT relevance** | Scoping, enumeration and reconnaissance phase | Exploitation and attack path demonstration |
| **Example** | 40 Internet-facing hosts, 3 VPN portals, 2,000 employee mailboxes | Phishing email leading to credential theft, then VPN login |

### Related Term: Attack Path

An **attack path** (or **attack chain**) strings together **multiple vectors and techniques** across the surface: for example, phishing (vector 1), credential theft, VPN access (vector 2), Kerberoasting, lateral movement and privilege escalation to the domain controller. Penetration testers document these paths because **individual low-severity findings often combine into critical risk**.

## 2.6 Master Glossary: How the Terms Interlock

| Term | Short Definition | Relationship to Others |
|------|------------------|------------------------|
| **Asset** | Thing of value | What risk is measured against |
| **Vulnerability** | Weakness | What a threat exploits |
| **Threat** | Potential for harm | Realized by a threat actor |
| **Threat actor** | Entity executing threats | Uses TTPs and tools |
| **Risk** | Likelihood x impact of loss | Product of asset, vulnerability and threat |
| **Exploit** | Method to abuse a vulnerability | Enabled by a vulnerability; delivers access |
| **Payload** | Post-exploitation action/code | Delivered after the exploit |
| **Zero-day** | Unknown, unpatched vulnerability | A special case of vulnerability with no defense yet |
| **Attack surface** | All exposures | The set within which vectors operate |
| **Attack vector** | Path of attack | A route through the surface |
| **IoC** | Observable evidence of compromise | Output of an attack; used for detection |
| **TTP** | Adversary behavior pattern | Describes how actors operate |
| **CIA** | Properties to protect | Defines what is at stake |
| **DAD** | Properties attackers violate | Inverse of CIA; defines attacker goals |
| **Control** | Safeguard | Reduces likelihood or impact of risk |
| **Residual risk** | Remaining risk after controls | What management accepts or treats further |

# PART 3: Integrated Scenario (Incident Response + Penetration Testing)

## Scenario: "Harborview Financial"

Harborview, a mid-sized financial services firm, has an Internet-facing customer portal, an Active Directory environment, a SIEM with Wazuh agents and Sysmon on endpoints, and nightly backups to a NAS reachable with domain credentials.

### Part A: The Attack (Adversary Perspective, Conceptual)

| Stage | Action | Terminology |
|-------|--------|-------------|
| 1 | The attacker enumerates Harborview's external presence and finds a VPN portal, a legacy web app and exposed employee names | **Attack surface** discovery; reconnaissance |
| 2 | A phishing email (vector) harvests an employee's credentials; MFA is SMS-based | **Attack vector**; **vulnerability** in people and weak MFA; **threat actor** is a cybercriminal affiliate |
| 3 | The attacker logs in to the VPN with valid credentials | **T1078 Valid Accounts**; confidentiality violated |
| 4 | Using the foothold, a Kerberoasting attack cracks a service-account password | **T1558.003**; **vulnerability**: weak service-account password |
| 5 | The attacker moves laterally and dumps LSASS on a server | **T1003.001**; **Disclosure** (DAD) |
| 6 | Data is exfiltrated to cloud storage | **T1567**; **confidentiality** violation |
| 7 | Logs are cleared and the backup NAS is reached with domain-admin credentials; backups are deleted | **T1070**, **T1490**; **Alteration** and removal of recovery capability |
| 8 | Ransomware is deployed to file servers | **T1486**; **Integrity + Availability** violated; **Destruction/Denial** (DAD) |

### Part B: The Response (SOC Perspective)

| Phase | SOC Activity | Key Concepts Applied |
|-------|--------------|----------------------|
| **Detection** | SIEM alert on impossible-travel VPN login; Sysmon Event 10 shows access to `lsass.exe`; Event 4769 spike with RC4 tickets | **TTP-based** detection (T1078, T1003.001, T1558.003) |
| **Triage** | Analyst maps activity to ATT&CK, identifies compromised account and affected hosts | Classify by **CIA/DAD**: C violated (credential theft), potential I/A impact imminent |
| **Containment** | Disable compromised accounts, isolate hosts via EDR, block exfiltration destination IPs and domains | **IoC** blocking plus behavioral containment |
| **Scoping** | Hunt for the same behavior chain (not just IoCs) across the estate | TTP-driven hunting |
| **Eradication** | Reset credentials (including KRBTGT twice if domain compromise is confirmed), remove persistence, patch and harden | Reduce **vulnerabilities**; shrink **attack surface** |
| **Recovery** | Restore from **immutable/offline** backup copy, validate integrity using **SHA-256** hashes and FIM baselines | **3-2-1-1-0**, **integrity verification**, **RTO/RPO** |
| **Lessons learned** | Replace SMS MFA with FIDO2, enforce strong service-account passwords (gMSA), isolate backup infrastructure, add Wazuh FIM on backup server | Update **controls**, document **residual risk** |

### Part C: Penetration Test Reporting Perspective

A good finding is written using precise terminology:

> **Finding:** Weak Authentication on Internet-Facing VPN Portal
> **Asset:** Remote access gateway and all internal resources reachable through it
> **Vulnerability:** SMS-based MFA and absence of phishing-resistant authentication; no conditional access
> **Threat:** Cybercriminal affiliates conducting credential phishing and adversary-in-the-middle attacks
> **Attack vector:** Phishing leading to valid-account VPN access (T1566 to T1078)
> **CIA impact:** **Confidentiality: High**, Integrity: High (lateral movement allowed config changes), Availability: Medium
> **Risk rating:** **High** (high likelihood, high impact)
> **Recommendation:** Deploy FIDO2/WebAuthn, enforce conditional access, monitor anomalous logins; **Residual risk:** Medium after remediation

## Key Takeaways

- **CIA** defines what defenders protect; **DAD** defines what attackers pursue. Classify every incident by **all** pillars affected.
- **Confidentiality:** AES-256 (with an authenticated mode and sound key management), **TLS 1.3**, RBAC/ABAC, and **phishing-resistant MFA**; the main threats are credential dumping, MitM and exfiltration.
- **Integrity:** SHA-256/HMAC, **FIM (Wazuh, Sysmon, auditd)**, **digital signatures and PKI**, secure development; the main threats are SQLi, ransomware encryption, supply-chain tampering and log manipulation.
- **Availability:** **HA, load balancing, BGP Anycast with scrubbing, 3-2-1-1-0 backups** with tested restores to RTO/RPO; the main threats are DDoS, resource exhaustion, wipers and ransomware.
- **Security versus usability** is managed through **risk-based, classification-driven and adaptive controls**, never by maximal enforcement everywhere.
- **Risk = Likelihood x Impact**, built from **asset, vulnerability and threat**; quantify with **SLE x ARO = ALE** and justify controls by cost-benefit.
- A **vulnerability is not an exploit, and an exploit is not a payload**; prioritize by **real-world exploitability and exposure**, not severity scores alone.
- **IoCs are perishable artifacts; TTPs are durable behaviors.** Use IoCs for speed and TTPs for resilience.
- **Attack surface = what is exposed; attack vector = how it is abused.** Reduce the surface, and break the vectors.
